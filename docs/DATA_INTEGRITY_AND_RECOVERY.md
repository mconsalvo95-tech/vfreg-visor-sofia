# VFREG data integrity, retention, and recovery

This policy applies to the local VFREG deployment directory. It keeps the
collector read-only toward the NT1-B and controls only files written by VFREG.

## Default retention and storage policy

| Data | Default policy |
|---|---|
| SQLite measurements | Keep 400 days (one year plus a 35-day buffer) |
| Collector events | Keep 400 days |
| Raw packet journal | 100 MB active file plus 5 rotated files |
| Application log | 10 MB active file plus 5 rotated files |
| SQLite backups | Every 24 hours, keep up to 7 verified backups |
| Runtime storage budget | 12 GB |
| Free-space warning | 5 GB remaining |
| Free-space critical state | 2 GB remaining |
| Maintenance cycle | Every hour and shortly after startup |

CSV and XLSX files generated by the dashboard replace the previous server-side
export. Copies downloaded to a user's Downloads folder are outside the VFREG
deployment directory and are managed by the user or company retention policy.

The application starts pruning before the 12-gigabyte limit. It first
removes expired backups and rotated raw journals, while always retaining the
newest database backup. If necessary, it removes the oldest measurements and
records a `STORAGE_BUDGET_PRUNED` event. SQLite reuses the released pages so the
database does not continue growing without limit.

These defaults are deliberately configurable under `storage` in
`config.factory.json`. Any longer legal or company retention requirement must
be approved together with a larger disk budget before changing them.

### Capacity assumption

The 12 GB policy is sized for a five-second production interval operating up to
eight hours every day. That produces about 2.1 million readings per year. Using
the measured pilot database and raw-journal footprint, the live database,
bounded raw evidence, logs, exports, and seven full daily backups are projected
to remain below approximately 8 GB after the 400-day window is full.

Selecting a one-second interval creates about five times as many readings and
is not covered by the 12 GB guarantee. A permanent interval below five seconds
requires a new capacity review; one-second annual retention would need roughly
40 GB of VFREG storage.

## Integrity evidence

- SQLite uses WAL mode so committed measurements survive an abrupt process
  exit.
- Every startup performs `PRAGMA quick_check`; a damaged database stops startup
  with a restore instruction instead of silently creating new history.
- Every backup is created with SQLite's online backup API and verified before
  it receives its final filename.
- Failed writes, a full queue, low free space, and storage-budget pruning are
  visible in the application log and `/api/status` storage health.
- Modbus timeouts create `DATA_GAP_STARTED` and `DATA_GAP_ENDED` events with the
  measured gap duration.
- Decoded rows carry a backend quality flag: `GOOD`, `UNVERIFIED`,
  `OUT_OF_RANGE`, `INCOMPLETE`, or `INVALID`.
- Manager CSV and XLSX exports remain limited to Time, Volts, mAmp, Frec, and
  Status; technical quality evidence remains in SQLite and the support API.

## Timestamp policy

The collector uses the Windows clock and stores timezone-aware ISO 8601
timestamps. CSV and XLSX exports remove the timezone suffix for readability but
preserve local date, hour, minute, and second. Company IT should keep Windows
time synchronization enabled. A manual clock change can make timestamps appear
out of chronological order even though SQLite row IDs retain arrival order.

## Manual backup

From a development or support computer with the locked environment installed:

```powershell
uv run --locked vfreg-maintenance --config config.factory.json backup
```

The command creates a verified file under `data/factory/backups` and applies the
configured backup count.

## Restore test and recovery procedure

Restoration must be performed while VFREG is stopped.

1. Close the VFREG console with `Ctrl+C` and confirm it exits.
2. Copy the entire deployment directory to separate storage before replacing
   anything.
3. Verify the selected backup:

   ```powershell
   uv run --locked vfreg-maintenance --config config.factory.json verify "data/factory/backups/vfreg-YYYYMMDD-HHMMSS.sqlite"
   ```

4. Restore only after the verification reports `PASS`:

   ```powershell
   uv run --locked vfreg-maintenance --config config.factory.json restore "data/factory/backups/vfreg-YYYYMMDD-HHMMSS.sqlite" --confirm
   ```

5. Run the preflight, start VFREG, and export a small known period to CSV.
6. Confirm the restored record count and timestamps before returning the
   collector to normal use.

The maintenance command refuses to run backup or restore while another VFREG
instance owns the deployment directory. Packaging the recovery command for a
Python-free factory PC remains part of the controlled deployment phase.
